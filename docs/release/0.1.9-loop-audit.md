# Voxa 0.1.9 voice-loop audit (issue #130)

The 0.1.9-rc2 voice loop was reported broken in four ways (issue #130): she played her reply but
**no sound came out and she interrupted herself**; and a **web search returned nothing**. This is
the audit: what was measured, what the root cause was, and what now stops it from coming back.
Nothing here was produced by playing sound or opening the microphone — every fix is gated by a
test that fails on the old code and passes on the new one.

## Bug 1 — playback was silent and she talked to a silent reference

**Symptom.** A reply reached the "speaking" state, the mouth moved on the timeline, but the
speaker heard nothing, and the app logged `reference silent: no echo possible`. With no reference
the barge-in attribution read a bare level rise as the user and cut her own reply off (Bug 2's
trigger).

**Root cause.** The render tap (`voxa/timeline.py:attach_render_tap`) that feeds both the sink and
the echo reference failed to attach:

1. `queue.set_property("async", False)` raised — the GStreamer `queue` element has no `async`
   property on 1.28, so the probe setup threw on every call.
2. `Pad.link(...)` returns `Gst.PadLinkReturn.OK`, an `int` whose value is `0`. `if not
   upstream.link(...):` therefore read a *successful* link as a failure and bailed.

Either way `attach_render_tap` returned `attached=False`, the reference pad stayed empty, and the
render path never reached the sink.

**Fix.** Guard the `async` property with `find_property` before setting it (both
`attach_render_tap` and `_attach_echo_probe`), and test link success with a `_pad_link_ok`
helper that treats `PadLinkReturn.OK` as success rather than a truthiness check.

**Gate.** `tests/test_playback_reaches_sink_and_reference.py` — a faithful fake Gst (queue with no
`async`, `Pad.link` returning `PadLinkReturn.OK == 0`) plus a real-GStreamer subprocess probe that
hands samples to the sink and the reference pad. Fails pre-fix, passes post-fix.

## Bug 2 — she interrupted herself on an empty transcript

**Symptom.** A level rise with `heard=''` immediately after `gate-open` became an INTERRUPT, so
Voxa cancelled her own reply on a transcript with no words in it.

**Root cause.** With the reference silent (Bug 1), attribution had no audio to work with and read
a bare level rise as the user. The transcript — the only thing that should decide what happens to
her words — was empty, but the code interrupted anyway.

**Fix.** In `voxa/bargectl.py`, before returning INTERRUPT, `_has_interrupt_words(heard, raw,
wake_word)` checks the transcript for a real word: empty, wake-word-only, or only hesitation/noise
markers (`[noise]`, `(inaudible)`, `uh`, `hmm`, …) is a **HOLD** (keep speaking, judge again),
never an INTERRUPT. A bare `stop` or `open the library` still always interrupts.

**Gate.** `tests/test_bargein_no_empty_interrupt.py` drives `BargeInController.observe` through a
settled baseline then a loud run with each transcript. Pre-fix the empty/wake-only/filler cases
returned INTERRUPT; post-fix they are HOLD while real words still INTERRUPT.

## Bug 3 — web search always returned "found nothing"

**Symptom.** Every question that needed a lookup fell through to the model with no results.

**Root cause.** `voxa/websearch.py` POSTed to `html.duckduckgo.com/html/`, which now answers these
requests with a `202` anti-bot "anomaly" page — 0 `result__a` markers — so `parse_results` found
nothing.

**Fix.** Query `lite.duckduckgo.com/lite/?q=` with a plain GET (no JS, real results) and parse its
`result-link` / `result-snippet` markup in `parse_lite_results`; the old `html/` POST is kept only
as a fallback when lite yields nothing.

**Gate.** `tests/test_websearch.py::test_parse_lite_results_real_url_title_and_snippet` (fixed
lite markup) plus a network test that skips cleanly when the endpoint is unreachable. Pre-fix the
parser function did not exist and the live search returned nothing.

## Bug 4 — a 0.1.8 config kept the old "webrtc" echo mode

**Symptom.** Upgrading from 0.1.8 left `echo_mode: "webrtc"` (its default) in the profile, so the
new neural DTLN stage never turned on.

**Root cause.** 0.1.9 changed the default `echo_mode` to `"dtln"`, but `ConfigStore.load` kept
whatever an old profile had stored, and there was no way to tell a stale default from an explicit
choice.

**Fix.** `Settings.echo_mode_user_picked` marker (set whenever the user changes the mode in
`voxa/window.py`). A profile with no marker that still carries the old `"webrtc"` default migrates
to `"dtln"`; a profile that explicitly chose `"webrtc"` carries the marker and is left alone.

**Gate.** `tests/test_config_migration.py` — the stale-default migration, the explicit-choice
guard, and a save/reload round trip that keeps the marker.

## Not reproduced here

The render-tap fix is on the **prerendered** path (the default `face_mode`, and both the "piece"
and "whole-reply" streaming paths). A **live/high** face renders through `playbin` (`_play_file`),
where the cross-bin tap still cannot attach — recorded here as still open, not fixed by this
audit. It is not the default and does not affect the reported silent-speech/echo bug.
